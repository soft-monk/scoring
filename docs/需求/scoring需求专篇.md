- 版本：v0.1（立项稿）

- **部署形态：后端 C++ 仓**（与 `decision-engine` 的定位一致；见 [`模块划分与缺口分析.md`](./模块划分与缺口分析.md) §3.4）

**关键差距（本专篇主要价值）**

> 需求初稿要求"推荐评分 93%、成功率 82%、推荐理由 4 条、预期效果 6 项"，
> 而今天这些数字**全部来自 `Seed.cc` 的写死值**，`optimizePlan` 是 `+3` 的假动作。
> 也就是说：**现场问"93% 怎么来的"，现在的代码答不出来。**
>
> [`模块划分与缺口分析.md`](./模块划分与缺口分析.md) §3.4 已给出结论：
> 必须拆成 **确定性评分（本引擎）** 与 **话术生成（`llm-provider`）** 两个 provider ——
> **"引擎算出 82%，LLM 只负责把它讲成人话"**。

## 1. 定位与边界

### 1.1 定位

```
输入（全部来自其它引擎 / 规则，只读）
  phase-engine 当前阶段 · resource-alloc 资源台账 · topology 链路评估 · entity-ledger 目标清单
        │
        ▼
┌──────────────────────────────────────────────────────────┐
│  scoring（C++，纯函数式，无 IO）                           │
│  CAND 候选生成 → NORM 指标归一 → W 权重评分 → PICK 排序推荐  │
│                      │                                   │
│                      ├──► EXP 可解释输出（逐项得分 + 理由）  │
│                      └──► OPT 自动优化（受约束的扰动重评）    │
└──────────────────────┬───────────────────────────────────┘
                       │ 评分结果（结构化，非话术）
                       ▼
   llm-provider：把结构化结论转成人话   ｜   宿主：落库 + 广播
```

**一句话**：scoring 回答"**每套方案得几分、为什么、哪套最好、优化能提升多少**"。
它**不产出自然语言**（话术归 `llm-provider`），也**不执行方案**（采用/确认的落库归宿主）。

### 1.2 为什么必须是独立引擎

1. **可解释性是可验收的**：初稿要求"推荐理由 4 条""预期效果 6 项"，这些**必须是评分过程的副产物**，不能事后编。
2. **可复现性是可验收的**：同输入同输出，才能回答"93% 从哪来"。
3. **它是"AI 推荐"与"规则兜底"的共同底座**：`TR-AI-02` 要求"LLM 不可用时规则引擎兜底"——兜底的就是本引擎。

### 1.3 范围边界

| 做 | 不做 |
|---|---|
| 候选方案生成（按规则，**不内建三套方案的名称与组成**） | 🚫 不做自然语言理由（`llm-provider`） |
| 指标归一与加权评分（权重由规则注入） | 🚫 不做资源分配的合法性校验（`resource-alloc`，本引擎只**读取**其结论） |
| 排序、推荐、置信度/评分输出 | 🚫 不做阶段推进（`phase-engine`，本引擎只**读取**当前阶段） |
| 可解释输出：逐项得分 + 贡献度 + 差值 | 🚫 不做落库与广播（宿主实现 `IPlanSink`） |
| 自动优化（受约束的扰动搜索） | 🚫 不做界面方案卡（宿主面板） |
| 采纳/确认的**状态语义裁决**（同侧唯一、幂等、前置条件） | 🚫 不做"生成执行任务"的业务动作（宿主 + `phase-engine`） |

### 1.4 硬约束

| 约束 | 取值 | 依据 |
|---|---|---|
| 现有接口形状 | `/plans` 返回行数组；`/plans/{id}/adopt|optimize|confirm` 返回方案行（`confirm` 额外带 `idempotent`）**不得破坏** | 契约 §3.3；`Api.cc` L588–645 |
| 事件名 | `plan.state`，负载含 `{missionId, side, planId, action}`，`action ∈ {adopted, optimized, confirmed}` | `Api.cc` L604/617/637 |
| 事件日志 | 采用与确认 MUST 落事件日志（`plan.adopted` / `plan.confirmed`） | `Api.cc` L606/640 |
| 幂等语义 | 已确认时 MUST 返回成功并标 `idempotent:true`（**不得报错**，否则前端流程会卡住） | `Api.cc` L628–630 原注释 |

| 演示数值 | 场景一推荐评分 93%、预期效果 6 项；场景二成功率 68/82/61% | 初稿 §6 T1-1/T5-1（**演示值，非指标**） |

## 3. 功能需求条目

### 3.1 候选生成（SCD-CAND）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| SCD-CAND-01 | **MUST** 候选由**规则驱动**生成：规则声明"若干套方案模板"（名称、组成、适用条件），引擎 MUST NOT 内建任何方案名 | 换规则即换候选；全仓检索 `多域协同压制` 零命中 | ⏳ |
| SCD-CAND-02 | **MUST** 候选生成可标注"不适用"：某套方案在给定资源/阶段下不可行时 MUST 标为不适用并说明原因，而非静默丢弃 | 资源不足时某方案标为不适用且原因可读；候选总数不减少 | ⏳ |
| SCD-CAND-03 | **MUST** 候选数量可变：支持任意套数（不写死 3 套） | 给 5 套模板即产出 5 个候选 | ⏳ |
| SCD-CAND-04 | **SHOULD** 候选去重：内容等价的候选 MUST 被合并或标注重复 | 给出两份等价模板 → 结果只留一份并说明 | ⏳ |

### 3.2 评分（SCD-SCORE）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| SCD-SCORE-01 | **MUST** 指标可配置：指标清单（key、名称、方向：越大越好/越小越好、量纲/范围）由规则注入 | 换指标集即换评分维度；引擎内无指标名硬编码 | ⏳ |
| SCD-SCORE-02 | **MUST** 归一化显式定义：每个指标 MUST 声明归一方式（线性区间 / 阈值映射 / 直接百分比），归一过程可复现 | 给定原始值可手算核对归一结果 | ⏳ |
| SCD-SCORE-03 | **MUST** 权重由规则注入，且 MUST 校验权重和（不为 0、可为 1 或自动归一） | 权重全 0 时报错；正常权重下总分落在 0–100 | ⏳ |
| SCD-SCORE-04 | **MUST** 总分 = 各指标归一值 × 权重之和，**计算过程 MUST 可导出**（逐项：原始值、归一值、权重、贡献度） | 导出结果手算可核对；93% 可由导出项复算出来 | ⏳ |
| SCD-SCORE-05 | **MUST** 输入显式声明：评分输入为结构化快照（资源台账 + 链路评估 + 目标清单 + 阶段 + 候选），引擎 MUST NOT 读全局状态或数据库 | 单测里只传快照即可算出分；引擎内无 SQL、无全局单例 | ⏳ |
| SCD-SCORE-06 | **MUST** 确定性：同输入 MUST 同输出，浮点结果 MUST 有明确舍入规则（避免 92.99999 显示成 93） | 同输入跑两次逐字节一致；边界值舍入符合规则 | ⏳ |

### 3.3 排序与推荐（SCD-PICK）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| SCD-PICK-01 | **MUST** 排序：按总分降序，分数相同时有**稳定的次级排序键**（如方案序号） | 同分候选顺序稳定可复现 | ⏳ |
| SCD-PICK-02 | **MUST** 推荐标记：输出"推荐方案 id"，且推荐 MUST 有可读理由 | 推荐项与最高分一致（或在规则声明例外时说明原因） | ⏳ |
| SCD-PICK-03 | **MUST** 允许强制选择非推荐方案（初稿 §10.3）：引擎 MUST 支持 `adopt` 任意候选，并在结果中标注"偏离推荐" | 采用非推荐方案时返回 `deviated:true` 与推荐项 id | ⏳ |
| SCD-PICK-04 | **MUST** 推荐理由生成：从评分过程派生 4 条（哪几项得分最高、与次优的差值、关键优势项） | 理由条目数达标且每条都能追溯到某个指标 | ⏳ |
| SCD-PICK-05 | **SHOULD** 与次优的差值输出：给出"领先第二名 X 分"，供界面"推荐评分"旁注 | 差值手算一致 | ⏳ |

### 3.4 可解释输出（SCD-EXP）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| SCD-EXP-01 | **MUST** 结构化输出：`{候选列表:[{id, 名称, 总分, 逐项得分[], 是否推荐, 是否适用}], 推荐id, 推荐理由[], 次优差值}` | 字段完整可机器消费 | ⏳ |
| SCD-EXP-02 | **MUST** 输出**不含自然语言话术**：理由为结构化条目（`{指标, 结论, 数值}`），人话由 `llm-provider` 生成 | 输出中无成句文案；换语言不需改引擎 | ⏳ |
| SCD-EXP-03 | **MUST** 审计可追溯：每次评分可导出"输入快照 + 权重 + 输出"三件套，供事后复盘 | 从存档可完整复算当时总分 | ⏳ |
| SCD-EXP-04 | **SHOULD** 敏感性提示：可选出"对总分影响最大的前 N 项" | 结果可复现且排序正确 | ⏳ |

### 3.5 自动优化（SCD-OPT）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| SCD-OPT-01 | **MUST** 替换现状假优化：`success_rate + 3` 这类硬编码 MUST 移除；优化 MUST 是基于**可声明搜索空间**的重评 | 全仓检索 `+ 3` / `99` 这类硬编码优化零命中 | ⏳ |
| SCD-OPT-02 | **MUST** 搜索空间由规则声明（哪些参数可调、步长、上下限），引擎在空间内扰动并重评 | 换搜索空间即换优化行为 | ⏳ |
| SCD-OPT-03 | **MUST** 优化结果可解释：输出"改了什么参数 → 哪些指标变了 → 总分变化" | 优化前后对比可逐项核对 | ⏳ |
| SCD-OPT-04 | **MUST** 单调性保证：优化后总分 MUST NOT 低于优化前（否则返回"无改进"而非更差结果） | 构造无改进场景 → 返回"无改进"，总分不变 | ⏳ |
| SCD-OPT-05 | **SHOULD** 有界与可中止：搜索 MUST 有迭代上限，且不阻塞调用方超过声明时限 | 超大空间下按时返回并说明已截断 | ⏳ |

### 3.6 采纳与确认裁决（SCD-DECIDE）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| SCD-DECIDE-01 | **MUST** 同侧唯一：同一 `side` 采纳/确认 MUST 互斥，后来者 MUST 使前者失效（语义由引擎裁决，落库由宿主执行） | 采纳 B 后 A 不再为 adopted | ⏳ |
| SCD-DECIDE-02 | **MUST** 幂等：重复采纳/确认同一方案 MUST 返回成功并标 `idempotent:true`，MUST NOT 报错 | 连点两次不报错、状态一致 | ⏳ |
| SCD-DECIDE-03 | **MUST** 确认前置校验：确认 MUST 校验方案当前状态（如是否已采纳、是否适用），不满足时给可读原因 | 未采纳直接确认 → 按规则拒绝或自动采纳（可配置），行为明确 | ⏳ |
| SCD-DECIDE-04 | **MUST** 事件与日志：采纳/确认 MUST 产出 `plan.state` 事件（`action` 保持 `adopted`/`optimized`/`confirmed`）与事件日志 | 事件名与负载与现状可比对 | ⏳ |
| SCD-DECIDE-05 | **SHOULD** 待确认态：支持"已生成但未采纳"的中间态可查询 | 三态（未采纳/已采纳/已确认）可分别列出 | ⏳ |

### 3.7 非功能性（SCD-NFR）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| SCD-NFR-01 | **MUST** 零外部依赖：无 Web 框架、无 SQL、无全局状态；纯计算 + 注入快照 | 空环境独立构建；跨仓 import 零命中 | ⏳ |
| SCD-NFR-02 | **MUST** 独立交付：独立构建、独立示例、独立测试、独立验收脚本（退出码 0/1） | 空环境 clone → 一条命令构建 → 一条命令验收 | ⏳ |
| SCD-NFR-03 | **MUST** 出口为反向接口：`IPlanSink`（方案状态变更）由宿主实现用于落库与广播 | 引擎内无落库与广播 | ⏳ |
| SCD-NFR-04 | **SHOULD** 性能：单次评分（10 候选 × 10 指标）≤ 1 ms；优化 ≤ 100 ms 或按时截断 | 实测达标 | ⏳ |
| SCD-NFR-05 | **MUST** 浮点可复现：同一平台同输入 MUST 逐字节一致；跨平台差异 MUST 在容差内并有说明 | 断言用容差而非等值比较 | ⏳ |

## 4. 引擎与规则的划分（policies）

| 属引擎（可复用） | 属规则（`policies/mapapp`，项目专属） |
|---|---|
| 候选生成机制、不适用标注、去重 | **三套编组方案与三套打击方案的名称、组成、适用条件** |
| 指标归一、加权求和、舍入规则 | **指标清单**（区域覆盖率/链路稳定度/…共 6 项；场景二的 4 项） |
| 排序、推荐、次优差值 | **权重表**（每指标权重） |
| 理由派生（结构化条目） | **理由条数口径**（4 条）与优先级 |
| 优化搜索框架、单调性、截断 | **搜索空间**（可调参数、步长、上下限） |
| 采纳/确认的状态语义与幂等 | **确认前置规则**（未采纳时拒绝还是自动采纳） |
| 审计三件套导出 | **演示数值的复刻口径**（93%、68/82/61%） |

**判据**：引擎公开接口里出现 `多域协同压制`、`93%`、`success_rate + 3` 即破线。
**特别注意**：引擎内 MUST NOT 出现任何**成句的推荐理由文案**——那是话术，属 `llm-provider` 或规则包。

|---|---|---|---|
| D1 | 引擎部署侧 | **后端 C++**，与 `resource-alloc` / `entity-ledger` 同构 | 全部条目 |
| D2 | 与 LLM 的分工 | **本引擎只出结构化结论**；`llm-provider` 只把结论转成人话。**MUST NOT 让 LLM 决定分数** | SCD-EXP-02；`模块划分与缺口分析.md` §3.4 |
| D3 | 现状假优化如何处置 | **移除** `success_rate + 3`，改为可声明搜索空间的重评；为演示兼容可提供"演示模式"开关，但 MUST 显式标注 | SCD-OPT-01 |
| D4 | 现有接口与事件形状 | **保持不变**（`/plans`、`plan.state`、`idempotent` 语义）；字段只增不改 | SCD-DECIDE-04 |
| D5 | 强制选择非推荐方案 | **允许**（初稿 §10.3），结果标注 `deviated` | SCD-PICK-03 |
| D6 | 浮点输出 | 对外输出**整数百分比**（与界面一致），内部保留双精度；舍入规则显式 | SCD-SCORE-06 |
| D7 | 采纳/确认的落库 | **引擎裁决，宿主执行**：引擎算"应该是什么状态"，`IPlanSink` 负责写库与广播 | SCD-NFR-03 |

## 6. 风险

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| R1 | 移除假优化后，演示"自动优化"可能看不出变化 | 现场观感下降 | 搜索空间按演示需要配置，保证首次优化必然有改进；同时保留"演示模式"并显式标注 |
| R2 | 指标口径未定（初稿 §10.2） | 无法定权重与归一 | 先按"演示级口径"落地，接口留替换点；`mission-baseline` 承载口径 |
| R3 | 引擎被写成"通用多目标决策框架" | 配置地狱、第二个消费者也难用 | 只支持"线性加权 + 归一 + 排序"，**不做多目标帕累托、不做机器学习** |
| R4 | 推荐理由被写成自然语言 | 与 `llm-provider` 边界破线、无法换语言 | SCD-EXP-02 用测试锁定（输出中不得含句末标点的成句文本） |
| R5 | 同侧互斥从数据库层搬到引擎后，并发下出现双采纳 | 状态不一致 | SCD-DECIDE-01 纳入并发验收用例 |
| R6 | 评分输入含"链路评估"，而 `topology` 未就绪 | 阻塞 | 输入为**可缺省快照**：缺项按"中性值 + 标注缺失"处理，不阻塞评分 |
